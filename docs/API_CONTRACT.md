# Open-participation annotation boundary (v1)

This supersedes the unpublished fixed-three-account prototype. The Pages site contains code and public Supabase configuration only. Never publish real sources, summaries, references, recovery codes, assignments/method mappings or responses. Synthetic test fixtures are allowed. Import the exact v2 guide/rubric and frozen templates privately through the coordinator SQL Editor.

## Anonymous identity and recovery

Use official Supabase Auth `signInAnonymously()`. New volunteers enter a display nickname only (trimmed1–40 characters, no control characters). Nicknames need not be unique and never authorize access. A backend-generated random participant ID remains stable across recovery. Authorization always uses the verified `auth.uid()` mapped in the unexposed private participants table; never trust user metadata or a client-supplied participant ID. Unauthenticated `anon` role cannot call the RPC. This version requires the current auth.users row to exist with is_anonymous=true on every application call; email/social sign-in or identity linking is not supported. Authenticated anonymous users may enroll or recover; ordinary application actions require an existing mapping.

The browser SDK persists its session across browser restarts using localStorage. A page is pinned to its Auth UID; if another tab changes identity, freeze its old workspace and require reload, and never execute queued old writes using a new identity. CAS still handles same-identity tabs. No implicit signout or new identity when recovery/sign-in transiently fails. Switching participant flushes pending writes and warns about retaining the recovery code. Never put credentials/codes/JWTs in URLs, logs, exports or source files. A nickname does not recover a session.

Recovery format is `SAL-` plus64 uppercase hexadecimal characters (256 random bits from browser crypto.getRandomValues). The frontend normalizes case and trims outer whitespace. SQL validates the format and stores only `sha256(convert_to(code,'UTF8'))` as bytea, never plaintext. Enrollment and recovery responses do not return a recovery code/hash; the client holds the code it generated. Display/download it for the user, explain that it is a private access key, and require confirmation that it has been saved before continuing. Keep a pending local backup only until confirmed; source/answers/reference are never stored with it.

Additional `annotation_api` actions:

- `enroll`, payload `{display_name,recovery_code}`: caller has a Supabase Auth UID but no participant mapping. Validate study/template availability. Atomically create a participant, choose one of3 balanced template schemes by round-robin under a settings-row lock, then materialize state-only assignments (134 retained records per volunteer;126 study plus2 active and6 archival practice) with unique opaque IDs and independently randomized frozen order per kind. Use deterministic hash ordering based on new random participant ID and template ID. Do not duplicate source payloads per volunteer. Same UID + same nickname/hash retry is idempotent; existing UID must never create a second participant or overwrite progress. Same nickname with different UIDs creates distinct volunteers. No name lookup API. Returns session payload with `enrolled:true`.
- `recover`, payload `{recovery_code,new_recovery_code}`: fresh Auth UID not already mapped to a participant. Atomically find participant by old hash FOR UPDATE, rotate to the new hash, rebind auth_user_id to the caller, preserve every answer/event/lock/order/acknowledgement, and record an identity_recovered event without codes/hashes. Old UID loses all participant access on completion; old recovery code is invalid. On response-loss retry, if new hash already belongs to this UID, return its session idempotently. Do not overwrite an already enrolled, different identity; require explicit switch first. Invalid code is a generic error, never returns a matching name or identity hint.
- `rotate_recovery`, payload `{new_recovery_code}`: mapped participant may generate a replacement private recovery code from its current valid session. Atomically replace hash and record event; no changes to work. Same-hash retry idempotent. Invalidate older recovery code and clearly warn the user before rotation.

Both nickname and recovery are rendered as inert text. Limit nickname length by Unicode characters consistently. Codes use fixed256-bit entropy, not human-chosen short strings. Recovery code hashes are coordinator-private too. Do not add weak name/password fallbacks. No public directory of volunteers.

## RPC and lifecycle

Single RPC: `public.annotation_api(p_action text,p_task_id text default null,p_payload jsonb default '{}') returns jsonb`. Use authenticated JWT plus publishable key. Only `authenticated` gets EXECUTE; all tables/helpers live in unexposed `annotation_private` with no anon/authenticated table/helper access. Enable RLS as defense in depth. SECURITY DEFINER boundary fixes empty search_path, qualifies all relations and checks Auth UID itself. A private participant row lock serializes ordinary actions against recovery, preventing an old-UID operation from succeeding after rebinding. No table API or client-writable stage flags.

- `session`: mapped user returns authenticated true, enrolled true, mode study, participant_id, display_name, accepted_instructions, tasks [{id,kind,position,status,stage}], progress {study_total,study_completed,practice_total,practice_completed,practice_requirement,paused}, rubric, guide_md. The queue contains126 study and only2 required practice tasks; practice_total and practice_requirement are2. Original task positions remain unchanged; the frontend presents the two active practice items as1–2. An authenticated UID without mapping returns authenticated true/enrolled false/needs_enrollment true without materials, names or other data. Frontend can show the nickname/recovery entry screen for this. Never automatically enroll in session.
- `acknowledge`, `{accepted:true}`: records guide acknowledgement once.
- `task`: ownership plus instructions gate; study additionally requires both persistent required practice tasks complete. Historical extra practice IDs remain accessible to their owner for stale-tab compatibility but are not listed in the active queue. Direct task response allowlist below.
- `save`, `{stage,revision,answers}`: partial nonempty valid stage-specific choices, row lock + exact revision CAS. Stage1 immutable after lock; Stage2 requires reference exposure; paused/complete cannot save.
- `lock`, `{revision,answers}`: exactly four Stage1 IDs. Atomically persist all4 and set stage2/status locked before reference access. Same-value retry idempotent, different values never overwrite a lock.
- `reference`, `{}`: ownership/gates/persisted Stage1 lock/stage2/nonpaused. Record first exposure once and increment revision, return only `{reference,revision,reference_released_at}`. No reference in any other participant action or static asset.
- `complete`, `{revision,answers:{reference_coverage:choice}}`: requires locked+exposed. Atomic immutable submit; same-value retries idempotent.
- `problem`, `{revision,category,criteria}`: existing fixed categories/criteria, separate structured event, pauses unfinished tasks without modifying answers/lock/exposure. Completed report never reopens. Stage1 reports cannot name reference_coverage.
- `export`, `{}`: own answer records/events only, split study_assignments/practice_assignments, including stable participant ID/display_name, hashes of materials, study/instruction fingerprints and acknowledgement. Never recovery code/hash, Auth token/UUID, article/reference text, private method mapping, or other participant data.

Unknown fields/actions, null/boolean/noninteger revisions, invalid choices/types, wrong stage, foreign IDs, extra task IDs on no-task actions and unexpected payloads are rejected. Use safe PostgREST HTTP SQLSTATEs PT400/PT401/PT403/PT404/PT409 (PT503 for missing setup/enrollment temporarily closed). No raw values in errors.

Task fields: id,kind,position,total,stage,status,revision,request,source,source_sha256,summary_a,summary_b,answers,locked_at,completed_at,reference_released_at. Never reference. Stage1 draft or paused-from-draft answers are partial Stage1 choices; otherwise only Stage2 choices. Original text, A/B mapping and exact v2 rubric remain unchanged.

Stage1 IDs: source_coverage,readability,faithfulness,content_focus. Stage2: reference_coverage. Choices: A,B,Tie. Problem categories: text_missing_or_unreadable,materials_appear_mismatched,cannot_interpret_material_reliably,accidental_selection_after_submission,other_interface_problem.

## Private seed schema (fixed interface)

- settings: id integer PK restricted1; schema_version text default open-participation-v1; study_fingerprint text; instruction_fingerprint text; rubric_version text; rubric jsonb; guide_md text; next_scheme bigint default0; enrollment_open boolean default true. No fixed participant count.
- templates: template_id text PK; scheme integer1..3; kind practice/study; position integer; payload jsonb with request/source/summary_a/summary_b/reference; hashes jsonb; coordinator jsonb SQL/JSON null or private object. Unique(scheme,kind,position). These are402 frozen templates (134 per scheme), seeded once. Scheme orientations reuse the established3 balanced/complementary schemes; they are not participant identities.
- participants: participant_id text PK opaque; auth_user_id uuid unique nullable FK auth.users(id) ON DELETE SET NULL; display_name text; recovery_hash bytea unique; scheme integer1..3; guide_ack_at timestamptz nullable; created_at timestamptz default now().
- assignments: task_id text PK opaque; participant_id text FK; template_id text FK; kind practice/study; position integer; practice_required boolean defaultfalse (true only for two practice rows per participant); stage integer default1; status draft/locked/complete/paused default draft; revision integer default0; stage1_answers jsonb default{}; stage2_answers jsonb default{}; locked_at/reference_released_at/completed_at timestamptz nullable; paused_from_status text nullable; updated_at timestamptz default now(). Unique(participant_id,kind,position). No duplicated payload/hashes/coordinator.
- events: event_id bigint identity PK; participant_id text FK; task_id text nullable FK; event_type text; revision integer nullable; payload jsonb; created_at timestamptz default now(). Never include recovery codes/hashes or auth tokens in events.

The private generator imports frozen templates/settings only, no participants or answers. Rerun is additive and fail-closed on changed material/schema; never reset work. The migration omits top-level BEGIN/COMMIT so the coordinator initializer can wrap it in a transaction. No destructive replacement of legacy state: fail with clear instruction if an incompatible prototype schema exists.

The additive two-practice migration retains all existing rows and snapshots. A private, participant-row-serialized helper selects exactly two required practice IDs once, prioritizing completed, then unpaused started, then unpaused untouched, then paused tasks. Existing IDs, positions, answers and lock state never change. Repeated migration/session calls keep the same subset. Exports retain all practice rows and their practice_required flags, so archival work is not lost. The migration locks the participants table before altering assignments to avoid lock-order inversion with in-flight RPCs. Run it in a transaction.

Coordinator-only private SQL functions: resolve_problem(p_participant_id text,p_task_id text) and export_all() including private matching metadata but no recovery_hash/Auth credentials. Only DB owner may call. Public volunteer responses make no claims about distinct natural persons, quality or representative sampling; coordinator vets data separately. Public signup should use Supabase's anonymous-Auth rate limits and, for broad public distribution, Turnstile/CAPTCHA. No automatic pruning of anonymous users or study records.
